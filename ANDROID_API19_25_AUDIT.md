# Android API 19–25 backport audit

## Scope and compatibility contract

This fork's requested deliverable is an Android sender for API 19–25 on `armeabi-v7a` and `x86`, able to connect to the **unchanged vanilla PepoMote PC receiver**. The desktop receiver and PMP v1 wire protocol are not to be modified. Keep existing product features wherever they can be backported; replace Android-only APIs/dependencies where needed. Do not present the backport as complete until the API-19 UI/build blockers below are resolved and tested.

## Current baseline findings

The checked-in Android client is the full Kotlin/Jetpack Compose client, not a tiny networking sample. `MainActivity.kt` contains routes for Connect, Controller, Nunchuk, Settings and the Android Server; `ControlClient.kt`, `UdpSender.kt`, `PmpCodec.kt`, `Discovery.kt`, `MotionEngine.kt`, `ScreenLink.kt`, and the Android receiver/server implementation hold significant functionality. Preserve these components and their behavior instead of replacing the app with a reduced gamepad-only screen.

The app Gradle file currently declares `minSdk = 26`, `targetSdk = 36`, `compileSdk = 36`, Java/JVM 17, Kotlin 2.1, Compose BOM 2025.06, AndroidX Core 1.16, Activity Compose 1.10, Lifecycle 2.9, ZXing Embedded 4.3, and uses the Compose UI source set. Those choices do not establish an API-19-compatible build. Compose itself has a higher platform floor than KitKat; simply lowering `minSdk` is not a valid backport. The required path is either to replace the Compose UI with legacy-compatible native Views or to split out a real API-19 UI source set while preserving the original feature logic and supplying compatible dependencies. The former has more risk but avoids shipping two UIs.

## Wire compatibility with vanilla PC

The client must continue speaking the receiver's documented PMP v1 contract: TCP JSON-lines `hello` with `pv:1` and either the four-digit `code` or saved `token`; receiver `ok` provides `session_id` and `udp_port`. The sender must preserve the correct 72-byte INPUT layout, and emit the 80-byte extension only in the modes/capabilities that the receiver confirmed. Keep the current golden vectors as compatibility tests. Do not add a fork-only handshake, change field names, or require a modified PC executable.

## Recommended implementation order

1. Keep this branch scoped to `android/**` plus Android-facing README/docs; leave desktop/iOS/mobile-Linux and receiver source unchanged.
2. Choose the API-19 UI plan and dependency/toolchain; replace Compose before claiming `minSdk 19`.
3. Fix manifest, QR, notifications/services, vibration and ABI packaging with API guards/fallbacks.
4. Audit storage, updater/install flows, sensors, discovery, screen stream and the Android server against API 19–25.
5. Run golden-vector/unit tests, build debug and release APKs, inspect merged manifests/ABIs, and device-test KitKat and Nougat against the unmodified PC receiver.

This audit is a source review, not a build or device-test result. Search output is not exhaustive; every call site and transitive dependency must be checked during implementation.
